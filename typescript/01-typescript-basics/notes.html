La Philosophie : Statique vs Dynamique

Cette section explore la différence fondamentale entre JavaScript et TypeScript. Vous y découvrirez pourquoi le typage statique est essentiel pour la fiabilité du code et visualiserez les avantages de TypeScript via une analyse comparative.

Comparaison des approches

  • 🟨
    JavaScript (Typage Dynamique) Les erreurs ne sont découvertes qu'à l'exécution (runtime).
  • 🟦
    TypeScript (Typage Statique) Ajoute une couche de règles vérifiées pendant le développement. Ton éditeur te prévient des erreurs en direct.
👑 La Règle d'or :

Le navigateur ou Node.js ne comprend pas TypeScript. Le code .ts doit toujours être compilé en .js pur. Au moment de la compilation, toutes les informations de type sont effacées (zéro impact sur les performances).

Inférence de Type & Le danger du "Any"

Cette section vous apprend comment TypeScript déduit automatiquement les types pour alléger votre code, et pourquoi le type 'any' détruit la sécurité de votre application.

✅

L'Inférence Intelligente

Si tu initialises une variable tout de suite, tu n'as pas besoin d'écrire son type explicitement. Le compilateur le devine.

let adoptableCats = 7;

// TypeScript sait automatiquement que
// adoptableCats est un 'number'
❌

Le Danger : Any

Une variable déclarée sans assignation initiale reçoit le type any.

let nextShiftStart;

// TypeScript lui donne le type 'any'
Pourquoi l'éviter ? Il désactive les vérifications. L'éditeur devient aveugle et tu perds l'autocomplétion.

Les Alias (Type) et les Annotations

Ici, vous apprendrez à structurer vos données de manière réutilisable. Évitez les "drifts" (désynchronisations de code) en centralisant vos contrats d'objets avec le mot-clé type.

Pour éviter de réécrire les mêmes structures d'objets partout, on utilise des Alias avec le mot-clé type.

1. Création de l'Alias

type Volunteer = { id: number; name: string; active: boolean; };

2. Utilisation

const member: Volunteer = { id: 12, name: "Nora", active: true, };

Les Interfaces et l'Héritage

Découvrez comment les interfaces complètent les alias. Cette section montre comment construire des contrats complexes à partir de blocs plus simples en utilisant l'héritage.

Les interfaces font quasiment la même chose que les type pour les objets, mais elles brillent par leur capacité à s'étendre (hériter) grâce au mot-clé extends.

interface Person {
  id: number;
  name: string;
}

// Coach récupère automatiquement 'id' et 'name' de Person
interface Coach extends Person {
  specialty: string; 
}

ES Modules : Isoler et Partager le Code

Apprenez à structurer une application qui grandit. Cette section explique comment utiliser les imports typés et illustre le pattern "Barrel" (Point d'entrée unique) pour garder votre code propre.

La Règle import type

Si tu n'importes qu'une Interface ou un Type, précise-le. Cela garantit que l'import disparaîtra complètement lors de la compilation en JS pur.

import { formatVolunteer } from "./volunteer.js"; // Fonction (valeur)
import type { Volunteer } from "./volunteer.js"; // Contrat (type)

Architecture : Le Pattern "Barrel"

Pour éviter d'importer depuis 50 fichiers différents, on utilise un fichier index.ts qui centralise tout. (Attention : en configuration NodeNext, on ajoute bien l'extension .js dans les imports !)
